# lu_solve_gpu under nixnan

CUDA LU-factorization solver (ported from the FPChecker tutorial's
`tutorial/example_1/lu_solve.cpp`, in `SC26-Tutorial-NixNan`) run under
`nixnan.so`, reproducing that tutorial's "bad matrix -> floating-point
exceptions" story on the GPU, plus two nixnan instrumentation configs:
exp-binade histogram gathering and an exponential `SAMPLING` sweep.

## Files

- `lu_solve_gpu.cu` -- self-contained CUDA LU solver (partial-pivoting LU +
  forward/backward substitution), solving `A x = 1` for a 20x20 matrix loaded
  from CSV. No dependency on the tutorial repo; CSV loading and residual
  helpers are inlined.
- `matrix.csv` -- well-conditioned input (residual ~1e-16).
- `bad_matrix.csv` -- ill-conditioned input; a near-zero pivot gets rounded to
  exactly 0.0 during elimination, and the resulting division by zero produces
  Inf/NaN that propagates through the whole solution and residual.
- `Makefile` -- `nvcc -arch=sm_86 -lineinfo` build (adjust `ARCH` for your GPU).
- `bin_spec.json` -- `BIN_SPEC_FILE` for exp-binade gathering (see below).
- `gen_bin_spec.py` -- regenerates `bin_spec.json`.
- `run_nixnan_experiment.sh` -- runs everything; outputs land under `logs/`.

## Running

```bash
cd ~/repos/nixnan/SC26-expts/lu_solve_gpu
./run_nixnan_experiment.sh
```

Requires a built `../../nixnan.so` (`cd ../.. && make`). Override
`NIXNAN_SO`, `CYCLES`, or `SAMPLING_MATRIX` via environment variables; see
the script header.

## Stage 1: exp-binade histogram gathering

`bin_spec.json`:

```json
{
    "count": 128,
    "doublings": 7,
    "max_reports": 0,
    "f16": [],
    "bf16": [],
    "f32": [],
    "f64": [[-1022, -1019], [-1018, -1015], ..., [1022, 1023]]
}
```

- **Precisions present**: `lu_solve_gpu.cu` only computes in `double`, so
  only `f64` is populated; `f16`/`bf16`/`f32` are left as empty arrays (valid
  per nixnan's schema, and correctly reported as absent).
- **Bucket size 4**: the `f64` array tiles the full valid double exponent
  range `[-1022, 1023]` (normal exponents only; subnormal/inf/nan exponents
  excluded) into 512 buckets of width 4, generated by `gen_bin_spec.py`.
- **`count: 128`**: report threshold. `count: 1` was tried first and produced
  ~13,700 report lines for a single run (nixnan reports on *every* occurrence
  past the first when `count` is 1) -- too noisy to be a "nice" histogram.
  `128` was chosen to match nixnan's own convention (its auto-generated
  template and the `SC26-expts/rd_nixnan` example both default to this
  order of magnitude) and produces ~100-150 threshold reports per run here.
- **`doublings`**: nixnan's docs (`../../README.md`, `../../Tutorial.md`)
  describe a `doublings` field for adaptive threshold scaling
  (256->512->1024->...->reset). As of this checkout, `src/fp-histogram.cu`
  never reads that key -- only `count` is used (see
  `record()` in `src/fp-fun.cu`: the report condition is
  `prev % count_threshold == 0 && prev != 0`, with no reference to a doubling
  schedule anywhere in `src/`). `doublings` is kept in `bin_spec.json` for
  schema/forward compatibility, but **it is currently a no-op in this nixnan
  build**. This is why the exponential schedule below (Stage 2) is
  implemented at the shell-script level instead.

Run:

```bash
HISTOGRAM=1 BIN_SPEC_FILE=./bin_spec.json LOGFILE=./logs/histogram/bad_matrix.log \
  LD_PRELOAD=../../nixnan.so ./lu_solve_gpu bad_matrix.csv
```

Observed on `bad_matrix.csv`: 63 binade-threshold reports, and a final
exception summary of **316 NaN / 4 Infinity / 4 Division-by-0** in FP64
operations (`logs/histogram/bad_matrix.log`). `matrix.csv` produces 99
binade-threshold reports and zero exceptions.

## Stage 2: exponential SAMPLING sweep

Requested schedule: `SAMPLING=1` for 16 runs ("snaps"), then `2` for 16, then
`4` for 16, then `8` for 16, then reset back to `1`.

nixnan reads `SAMPLING` once at process startup
(`GET_VAR_INT(sampling, "SAMPLING", ...)` in `src/nixnan.cu`) -- there is no
supported way to change it mid-run. So each "snap" here is one full process
launch of `lu_solve_gpu bad_matrix.csv`, and the schedule is implemented as a
loop over `(level, snap)` pairs in `run_nixnan_experiment.sh`, storing each
run's log at `logs/sampling/cycle_NN/sampling_<level>/snap_NN.log` (plus a
`.stdout` file with the program's own solution/residual output). Default is
one full pass through the schedule (`CYCLES=1`); set `CYCLES=2` to also see
it reset and repeat.

**Finding: `SAMPLING` has no observable effect in this nixnan build.**
`bad_matrix.csv`'s elimination kernels are each launched ~19 times (one per
pivot step of the 20x20 matrix), so `SAMPLING={1,2,4,8}` should visibly change
how many of those repeat invocations get instrumented. It doesn't: the
`snap_01.log` files for `SAMPLING=1` and `SAMPLING=8` are byte-identical
(diff empty), as are all 16 snaps within a single level (all 16
`sampling_1/snap_NN.log` files share one MD5). Reading `src/nixnan.cu`:

- The per-kernel invocation counter used by the `SAMPLING` skip check
  (`should_instrument()`, `analyzed_kernels.count(func_name)`) is looked up
  by `func_name = nvbit_get_func_name(ctx, f)` -- the **full** signature,
  e.g. `eliminate_kernel(double*, double const*, int, int)`.
- The counter is actually incremented in `nvbit_at_cuda_event()` under
  `short_name = cut_kernel_name(kernel_name)` -- the name truncated at the
  first `<` or `(`, e.g. `eliminate_kernel`.
- Since these two keys never match for any kernel with a non-empty parameter
  list (i.e. essentially all real CUDA kernels), `analyzed_kernels.count(func_name)`
  is always 0 inside `should_instrument()`, the sampling-skip branch never
  runs, and every kernel invocation is instrumented regardless of `SAMPLING`.

This looks like a real bug in `SAMPLING` (key mismatch between the launch
counter map and the sampling lookup), not a property of this experiment --
worth fixing upstream in nixnan itself. The 16-snaps-per-level logs are still
stored as requested; they currently demonstrate the *schedule/harness*
faithfully, not a behavioral difference, since `lu_solve_gpu` is deterministic
and `SAMPLING` is not (yet) actually filtering anything.
